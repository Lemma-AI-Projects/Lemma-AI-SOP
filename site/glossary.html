术语与约定

本文件定义 SOP 文档里出现的术语。

术语的权威解释只有这一处。其他文档只使用它，不另行解释。若某份 SOP 里的话与本文件冲突，以本文件为准。

一个术语除了"是什么"，还必须知道"什么时候不该用它"——所以每条都带一列边界。只写定义会让人以为这个词管一切。

一、协作空间

回答"这条信息该写在哪"。

术语定义边界：什么时候不用它出现于
提案区尚未形成正式判断的 Idea、机会、问题、风险。一切还没被团队讨论过的东西先落在这里。已经讨论出结论、要作为团队行动依据的内容不留在提案区，应当进入正式文档区。SOP-1、备忘录
自我曝光文档个人的不同时间尺度计划、当前工作与思考。每个人有自己的一份，其他人可以查看。不放团队级决策，也不放需要他人同步执行的任务；只反映本人的计划与状态。SOP-1、备忘录
正式文档区团队讨论后形成的正式计划、决策、知识和对外信息。团队对外表达的最终依据。不是草稿箱。未经讨论、未定稿的内容不进入；个人计划也不进入。SOP-1、备忘录
飞书多维表格用于实际工作协同与状态同步的工具载体。不是知识沉淀的地方。状态协同放这里，经验与知识放正式文档区。SOP-1、备忘录（备忘录中称作"多维表格"）

流转规则：想法先落提案区 → 讨论定稿后才进正式文档区 → 个人计划只进自我曝光文档 → 日常状态同步走飞书多维表格。

二、阶段

回答"一件事走到哪了"。

术语定义边界：什么时候不用它出现于
想法 / Idea任何成员发现的新机会、新需求、新问题。不要求成熟，但应能说明"为什么想到它、它可能解决什么问题"。还没被讨论、没有判断的原始念头才是"想法"；一旦团队开始讨论，它就成为"决策"环节的议题。README、SOP-1
决策 / Decision团队讨论一个想法是否值得做的环节。判断"为什么现在做、解决什么真实问题、是否符合当前方向、成本与收益如何、最大的不确定性是什么"。只有团队讨论才叫决策；个人自行决定不叫决策。结果只有四种：做 / 不做 / 暂缓 / 先验证。README、SOP-1
交付 / Delivery将决定转化为可运行的产品，原则是"最小实现，尽快获得真实反馈"。交付不等于上线。未经验收的实现不是交付完成。README、SOP-1
上线 / Launch通过验收后让功能投入使用。上线不是结束，而是开始获得真实反馈。上线不自动等于对外公开；对外的判断标准更严（见"对外"）。README、SOP-1
对外 / External需要对外公开时，确认功能是否已达到可以代表 Lemma 对外表达的标准。不是每个功能都需要对外。标准未达到时，功能可以上线但不对外表达。README、SOP-1
反馈 / Feedback上线后观察真实使用情况，可能产生：继续迭代 / 修改判断 / 新 Idea / 新技术问题。反馈不是意见收集；只有能改变后续判断（继续、修改、新增）的信息才算反馈。SOP-1

三、文档与角色

术语定义边界：什么时候不用它出现于
SOP规定团队如何思考与信息如何流转的文档，不规定每个功能必须采用完全相同的开发方式。不是技术方案、不是排期表、不是操作手册。具体做法由各成员自行判断。README、SOP-1
元帮助前三份 SOP 解决不了的问题来看的那一份。不是常见问题清单，也不是求安慰的地方；它处理的是"连流程本身都不适用"的情况。README、备忘录（尚未成文）
质量验收 / Verification交付与上线之间的把关：功能是否正常？是否真正解决了最初的问题？不是代码审查，也不只看"能不能跑"；要回答的是不是解决了最初的问题。README、SOP-1
知识与新人 / Knowledge沉淀下来的经验与知识，供团队和新人理解，进入正式文档区。不是个人笔记，也不等于开发细节；能让下一个人不从零开始的内容才算。README、SOP-1

四、尚未定义的

以下内容目前故意没有全局规定。各份 SOP 写到时会单独说明，在此之前不要自行脑补统一规则：

  • 改动多小算小、可以不走完整流转的门槛
  • 对外发布由谁确认、谁有否决权
  • 谁对最终决定拥有拍板权
  • en/ 英文版的对应术语
  • README 结构图里的 Trigger / Standards / Process / Artifact / Decision / Feedback / Knowledge / Principles——它们目前只是图上的结构标签，不是团队日常语言，暂不定义
